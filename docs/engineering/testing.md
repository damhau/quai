# Testing strategy

Status: Draft · 2026-11-09

## Tiers

Tests run in three tiers, so that work does not wait for what a later tier catches.

| Tier | When | Who waits for it | What |
| --- | --- | --- | --- |
| **1. Quick** | Before each commit, locally (`make quick` in `backend/`; `npm run typecheck && npm run lint && npm run test` in `frontend/` when it changed; `make -C plugins check` when `plugins/` changed) | The developer or the session | Build and vet everything; staticcheck and the tests, without `-race`, of the changed packages and of those that import them (or whose tests do); `sqlc diff` when queries or migrations changed; `quai lint` on the example repository when it changed |
| **2. Full** | On every push, in CI (`backend.yml`, `frontend.yml`, `packaging.yml`, `plugins.yml`) | Nobody: the next iteration reads the previous push's result before it starts, and a red one is fixed first | `make check` in parallel jobs (static checks, `internal/api`'s tests, the other tests, all with `-race`), each restoring Go's build cache from the previous commit and the tools from their own cache; the frontend, the chart lint and the image build and smoke test; the plugin SDK, template and example (`make -C plugins check`) |
| **3. Slow** | Nightly, and on demand before a phase review or a milestone (`gh workflow run`) | The phase review and the milestone: they close with tiers 2 and 3 green on the same commit | The Playwright scenarios (`e2e.yml`), the Helm chart on kind (`kind.yml`), the image's vulnerability scan (Trivy, `packaging.yml`), the live tests on the Azure DevOps and GitHub sandboxes (`live.yml`) |

Tests that need no shared state run in parallel (`t.Parallel()`) where they are slow: each has
its own database (`pgtest`) and its own Gitea repositories. At most four use a package's Gitea at
once (`giteatest`): it runs on SQLite, and its queues fall behind under more. The live tests on
the sandboxes stay sequential: the Azure DevOps sandbox has one pipeline agent, and GitHub limits
how fast an app creates content.

Principles:

- **The engine is tested hardest.** It decides what gets written to customer repositories. Target 90 %+ line coverage in `internal/engine`, plus fuzzing.
- **Every editing bug becomes a corpus case** before it is fixed.
- **No mocks for PostgreSQL or Git.** Use the real thing; mocks for these hide exactly the bugs that matter. Tests start their own PostgreSQL with embedded-postgres: a real server process, listening on TCP only, whose binaries are downloaded once into the user cache directory. It needs no Docker and runs inside the agents' sandbox, where commands have their own network namespace and cannot reach a container's ports. Code that reads Kubernetes gets a real API server the same way (`internal/k8stest`): the `kube-apiserver` and `etcd` of the envtest release, checksum-verified, downloaded once and started with controller-runtime's envtest. It has the CRDs the components render for installed (Argo CD's `Application`, Flux's `Kustomization`, Crossplane's `CompositeResourceDefinition`), vendored from their upstream releases into `internal/k8stest/crds/` by its pinned `refresh.sh`; a claim's CRD, which Crossplane generates from an XRD at run time and no release publishes, is made by the test from the example's XRD the same way. The manifests the components render, and those of `examples/kubernetes-repo`, are checked against it in server-side dry runs. WebAssembly plugins are built by the tests from Go sources (`internal/engine/generate/plugin/testdata`, and the repository's `plugins/ini` and `plugins/template`, through `plugintest`), with the toolchain that runs them (`GOOS=wasip1 GOARCH=wasm`, `-buildmode=c-shared`): no module is downloaded or checked in, and the runtime runs exactly what Quai runs. Git transport is tested the same way, in process: `internal/gitx` serves its test repositories with `git http-backend` over HTTPS, with a certificate from a test CA and a server that requires the credentials header, through a CONNECT proxy, and over SSH from a Go SSH server. Gitea runs the same way (`internal/giteatest`): the release's binary (the version the compose stack runs), checksum-verified and downloaded once, started on a free local port with SQLite, an admin user and a token, with helpers for throwaway repositories, users, branch protection and webhooks. Mail goes to Mailpit the same way (`internal/mailtest`, the version the compose stack runs). CI caches these downloads (`~/.cache/quai`). Azure DevOps tests run live against the sandbox organization through `internal/adotest`, skipped without its PAT; Azure DevOps cannot reach a test machine, so its webhooks are tested by replaying what it tried to deliver, read back from the service hook subscription's history. GitHub tests run live the same way against the sandbox organization, as a GitHub App, through `internal/githubtest`, skipped without the app's key ([what the sandbox holds](../plan/phase-3-backlog.md#test-infrastructure)); their webhooks are replayed from the app's delivery history, with the signature GitHub made. Containers are for what has no lighter form (the compose stack).
- **Prototype tests are ported first.** The TypeScript tests (expressions, policy, rendering, `patchYaml`, the API scenarios including stale approvals) become the first Go tests, so the port starts from proven behaviour.
