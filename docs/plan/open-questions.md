# Open questions

Status: Draft · 2026-11-08

## Still open

A decision the docs do not settle is added here, with the default the plan assumes until
the owner answers it. Until M2 closes, work goes on with that default, unless the choice is
security-sensitive or hard to reverse (decided below). Numbers are not reused: the next question
is 31.

| 13 | How the GitHub connector learns which GitHub App it is, and which installation | A connection had one secret and nowhere for an app's ID, and an installation's ID is one more value for an admin to find and keep right | **`spec.credentials.appId` holds the app's ID, in the document since it is public, and `spec.credentials.ref` the private key.** The installation is found from them (`GET /repos/{owner}/{repo}/installation` with the app's JWT, checked on the sandbox), kept in memory, and looked up again after GitHub refuses a token. Tokens are limited to the connection's one repository, whatever the app is installed on ([GitHub](../design/12-git-connectors.md#github-second)). The wizard asks for the app's ID since P3-18 | GA |
| 14 | What makes the definitions trusted on GitHub: a `CODEOWNERS` rule covering `.quai/`, a branch rule requiring code owners' review, or both ([#131](https://github.com/damhau/quai/issues/131) reads "`CODEOWNERS`, or rulesets requiring code owner review") | On GitHub, `CODEOWNERS` alone only requests reviews, so anyone who may approve can merge a change to `.quai/`; a rule requiring code owners' review alone requires nothing of `.quai/` unless `CODEOWNERS` covers it | **Both**: `CODEOWNERS` covering `.quai/` (read as GitHub reads it), and the branch requiring code owners' review in a ruleset or branch protection; each missing part is a trust problem ([trust](../design/01-repository-connections.md#trust)). Accepting either would show an untrusted repository as trusted | GA |
| 15 | How GitHub's webhooks reach Quai: a webhook on each repository, or the GitHub App's own webhook | The app's webhook is one URL and one secret for every repository the app is installed on, while Quai's endpoint is per connection (`/webhooks/<name>`) and verifies with the connection's own `spec.webhooks.secret`. A repository webhook needs the app's Webhooks (read and write) repository permission, or an admin to add it by hand | **A repository webhook per connection**, at `/webhooks/<name>` with `spec.webhooks.secret`, installed by `Subscribe` when the app has the Webhooks permission, otherwise added by hand as the health page says ([GitHub](../design/12-git-connectors.md#github-second)). The app's own webhook is not used. The connector parses its deliveries the same way and drops another repository's, so an app-wide route, fanning one delivery out by repository, can be added later without changing the connector | GA |
| 16 | How the pull requests people open themselves (a new type in `.quai/`, a Terraform module, a pipeline) merge on a branch that requires `quai/approval` | The status check applies to every pull request, with no path filter, and only Quai's identity may post it ([Azure DevOps](../design/12-git-connectors.md#azure-devops-first-services-then-server)); Quai posts it only on its requests' pull requests. So once a repository is onboarded, no one's own pull request completes without a policy bypass: on `pilot-infra`, P3-19's pull requests !407 to !410 passed their build validation (runs 173 to 176) and wait on it | **The platform owners complete them with a policy bypass**: Azure DevOps' "Bypass policies when completing pull requests" (GitHub: a ruleset bypass entry), given to their group only, after the `/.quai/*` reviewers approve. Quai's identity never has it, so `quai/approval` still binds Quai, and no one posts `quai/approval` by hand on a pull request Quai did not open: that would be an approval Quai never gave. Quai reviewing such pull requests under rules of its own would be Phase 4 work | P3-19 (#133) on `pilot-infra`; every repository onboarded after its status check |
| 17 | How a GitHub user named in `CODEOWNERS` (`@alice`) matches a Quai user | Open question 9 names Azure DevOps and Gitea, and was decided before the GitHub connector; GitHub does not give an app its members' emails | **The repository document's mapping first** (`spec.codeowners.mapping`, which takes users as well as groups: `@alice` → `user:alice`), **then their email in the organization's verified domains** (GraphQL `organizationVerifiedDomainEmails`, built in P4-00). Otherwise the entry matches no one and is shown on the request, as for Azure DevOps and Gitea. Measured on the sandbox `damhau-quai-sandbox` with the app's installation token (Members: read), 2026-11-08: `user(login:){organizationVerifiedDomainEmails(login:)}` answers without error and returns an empty list for the organization's admin; `organization{domains}` is FORBIDDEN to the app; a free organization cannot verify a domain. So the email path is tested against a fake GraphQL server only, and the live test matches GitHub users through the mapping. To check with an organization that has a verified domain (Team or Enterprise plan) | GA |
| 18 | How an audit event is serialized for its hash | Design 09 says "canonical JSON" without naming a form; the form cannot change once a chain exists | **RFC 8785 (JSON Canonicalization Scheme)** over the event without `prev` and `hash`: `hash = SHA-256(prev ‖ JCS(event))`, `prev` of the first event 64 zeros. Personal data (names, emails, IP addresses, reasons) is in the event as the SHA-256 of a random salt and the value, the salt and the value kept in a separate table that pseudonymization deletes from ([data protection](../design/09-security-and-compliance.md#data-protection)) | P4-01 (#138) |
| 19 | How the audit table is made insert-only | Design 09: "an insert-only database role"; today one database URL serves `quai migrate`, the server and the worker, and retention must delete old events | **Two roles.** `quai migrate` connects as the schema owner (`database.migrateURL`, falling back to `database.url`); the server and the worker as an application role with `SELECT` and `INSERT` on the audit tables and nothing else there. Pruning goes through a `SECURITY DEFINER` function that deletes only events older than the retention and covered by a signed checkpoint. When both URLs are one role (the compose stack), the health page says the database does not protect the log | P4-01 (#138) |
| 20 | How IdP groups map to Quai teams | Design 08 names "a configurable mapping (`groups: [sg-quai-*]` → teams)" without its form; today a team is the group of the same name | **`auth.teams`, a list of `{group: <pattern>, team: <name>}`**, where `*` in the team stands for what `*` matched in the group (`{group: sg-quai-*, team: "*"}`: `sg-quai-shop` is team `shop`). A group no entry matches is the team of its own name, as today | P4-04 (#141) |
| 21 | Where types and blueprints declare their entitlements | Design 08 shows a `catalog:` block, but a type's `spec.catalog` is already `visible` or `hidden` | **`spec.entitlements`** on types and blueprints: `visibility` and `requesters` (group patterns or `user:<name>`; empty does not restrict), and `environments`, keyed by the value of the `env` param (types) or input (blueprints), each narrowing `requesters` for that environment. `quai lint` refuses `environments` on an item with no `env` | P4-05 (#142) |
| 22 | Whether a link in a Teams or Slack message approves on its own | Design 11: the button opens "a signed, short-lived link bound to the approver and the change set hash", re-authenticating only for step-up rules; on its own, such a link is a bearer credential kept in a chat system | **No.** The link opens the request with the decision ready; confirming needs a Quai session as that approver (with single sign-on, usually one click), and the link's binding makes sure it is that person and that content. Rules with step-up re-authenticate first | P4-09 (#146), P4-10 (#147) |
| 23 | Where the separation-of-duties options are set, and who is a definition author | Design 05 names `separationOfDuties.definitionAuthors: 7d` and `destroys: requireTwo` but not where; in a type, the change they guard could remove them | **The repository document**, `spec.enforcement.separationOfDuties` (admin-owned, like floor rules). A definition author is the Git author of a commit that changed the type's or blueprint's files (its schemas included) within the period before the request's definitions commit, matched to a Quai user by email as in open question 9 | P4-12 (#149) |
| 24 | What a delegate may do | Design 05: "delegate to a named colleague for a date range", nothing on scope | **What the delegator could approve or deny, during the range**, recorded "by X on behalf of Y". X counts once, for Y or for X; never on a request X or Y made; a delegate cannot delegate further | P4-13 (#150) |
| 25 | Where reminders and escalation are configured, and what escalation does | Design 05: "after a configurable delay", "escalation goes to a fallback group", without where, or whether that group may approve | **Quai's configuration** (`approvals.reminders.after`, `approvals.escalation.after`, `approvals.escalation.to`), which the repository document can override. **Escalation notifies the group; it does not make it an approver**: who may approve stays the rules' decision | P4-14 (#151) |
| 26 | Where change windows are declared | Design 05 shows `changeWindows` without its place | **Quai's configuration** for windows across repositories (a year-end freeze) and **the repository document** (`spec.enforcement.changeWindows`) for one repository; both apply. Not in types, which could otherwise open their own window. `when` sees the request's params, type and kind | P4-16 (#153) |
| 27 | Who signs off a break-glass review, and who "security" is | Design 05: "security and the owning team are alerted", "until two reviewers sign it off" | **Two people other than the one who broke glass and the requester, each a platform admin, an auditor or a member of the owning team.** "Security" is the alert recipients of the notifications configuration (`notifications.alerts`, P4-07) | P4-17 (#154) |
| 28 | ServiceNow: which changes are standard, how Quai learns a change request's state, how it authenticates | Designs 05 and 11: standard changes "for catalog items marked as pre-approved", without where they are marked; nothing on how the state comes back | **Quai's configuration maps catalog items to standard change templates** (`itsm.servicenow.standardChanges`), so pre-approval stays with Quai's admins and ServiceNow's change board; other items get normal changes. **Quai polls** the change requests it waits on (every 5 minutes, and when the request page opens): ServiceNow needs no access to Quai. OAuth client credentials or basic authentication of a service account, as secret references | P4-19 (#156) |
| 29 | How the repository document maps the platform's owners, and when Quai reads them | Open question 9 decided that platform groups match through a mapping in the repository document, without its form; the code owners of a change can also move between plan, submission and review | **`spec.codeowners.mapping`**: keys as the platform writes owners (without regard to case or a leading `@`), values `group:<name>` or `user:<name>`; tried before any email, so an admin can correct a wrong match ([identity](../design/08-identity-access-tenancy.md#directory)). The code owners of a request are **every owner of every changed path**, on the target branch at the plan's commit, read again when the branch moves and kept for a minute; they are **kept with the request when it is submitted**, so a later `CODEOWNERS` change does not change who may approve it (submit again to pick it up). **When the platform cannot be read**, a plan that needs them fails (503) and resources owned through them have no owner until it can: no rule or resource falls back to fewer owners | GA |
| 30 | Whether a Quai user's unverified email matches an owner | Matching code owners by email lets whoever controls an address approve as its owner; some IdPs let users set their email | **No: an email the IdP marks unverified (`email_verified: false`) is ignored**, as if the user had none; an IdP that sends no `email_verified` is trusted for the email it sends.
