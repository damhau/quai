## Decided

| Question | Decision | Date | Consequences |
| --- | --- | --- | --- |
| Whether GitHub Enterprise Server is part of M2 (open question 11) | **github.com only.** GHES is a future improvement, scheduled when a customer needs it; the connector keeps the API URL configurable | 2026-10-31 | P3-16 to P3-18 are built and accepted on github.com, where the conformance suite runs; epic #52 no longer requires GHES; GHES support is [#137](https://github.com/damhau/quai/issues/137) ([roadmap](roadmap.md#future-improvements)) |
| Whether Quai's approval is the only authority, or Azure DevOps required-reviewer policies must also pass (open question 3) | **Quai is the sole authority** ([ADR 0002](../adr/0002-quai-is-the-approval-authority.md)) | 2026-10-31 | Branch protection requires `quai/approval` alone; the platform's path-based reviewers count through the `codeowners` approver kind, from Phase 4 (#100) |
| Which PostgreSQL major version Quai supports (open question 6) | **PostgreSQL 17** | 2026-10-31 | The tests (embedded PostgreSQL), the compose stack and the kind fixtures run 17; another version is added when a customer needs it |
| What an approval rule on `plan.*` does before the plan reports (open question 7) | **It is undecided until the plan reports**, as built in P2-05 and P2-12 ([rules on the plan](../design/05-delivery-and-approvals.md#rules-on-the-plan)) | 2026-10-31 | The request cannot reach *Approved* before the plan, approvals given meanwhile stand, and the rule is evaluated again for each new plan; with direct delivery, or when the plan cannot decide the condition, the rule applies |
| Which Azure Pipelines pipeline plans, applies or checks drift for which stack (open question 8) | **`spec.runner.pipelines`**: one entry per pipeline, with its kind (`plan`, `apply`, `drift-check`) and the stacks it covers, as built in P2-09 ([adapters](../design/06-runs-status-and-drift.md#adapters)) | 2026-10-31 | `quai report` still names the stack it reports |
| Where the Azure DevOps Server conformance tests run (open question 1) | **Both**: a Server 2022 lab VM for nightly runs (licensing to check), and a test project on the customer's Server for acceptance | 2026-10-31 | Applies when Server support ([#98](https://github.com/damhau/quai/issues/98), a [future improvement](roadmap.md#future-improvements)) is scheduled |
| How the first Server customer's installation is set up (open question 2) | **One collection holds the IaC repositories, the `/tfs` virtual directory is in use, a project collection administrator does the setup once** (the service account's branch-folder permissions with `tf git permission`, the service hook subscription), **PATs last at most 1 year** | 2026-10-31 | URL parsing, the registration wizard and PAT rotation reminders are built on these when #98 is scheduled, and checked with that customer then |
| Whether an ITSM tool must hold change records (open question 4) | **ServiceNow, in Phase 4** | 2026-10-31 | Change requests and the `external: servicenow` approver ([delivery and approvals](../design/05-delivery-and-approvals.md#itsm), [integrations](../design/11-integrations.md#itsm)) are Phase 4 scope; Jira Service Management only when a customer needs it |
| How an owner named by the Git platform (a `CODEOWNERS` entry such as `@alice` or `@org/team`; an Azure DevOps reviewer such as `alice@acme.ch` or `[Project]\Platform`) matches a Quai user or group (open question 9) | **Users by email, groups by an explicit mapping**: Azure DevOps account names and email entries as written, Gitea users through the email the connector reads; platform groups through a mapping in the repository document (platform group → Quai group); unmapped entries match no one and are shown on the request | 2026-10-31 | The `codeowners` approver kind (Phase 4, #100) follows it, and the reviewer's email is kept with their review ([identity](../design/08-identity-access-tenancy.md#directory)) |
| Where the envtest dry runs get KubeVirt's `VirtualMachine` CRD, which KubeVirt publishes no file for (open question 12) | **Nowhere: `kubevirt.vm` leaves P3-10.** The only KubeVirt GitOps repository we know declares its VMs as entries of each site's Helm values (`componentValues.vms.vms`), which the `entry` locator already edits (checked with `quai lint` and a golden example on a copy); its own chart renders the `VirtualMachine` | 2026-10-31 | P3-10 (#124) builds the `dir` locator and the `component` generator with `raw` and `k8s.namespace`, whose kinds envtest knows without CRDs; `definitions` no longer accepts `kubevirt.vm`. The renderer is a [future improvement](roadmap.md#future-improvements) (#136), with a refresh script that installs the pinned KubeVirt operator in kind and saves its CRDs |
| How Quai learns an apply's result when neither Azure DevOps' service hooks nor the pipelines' `quai report` step can reach it (open question 10) | **Quai polls**: at each poll it reads the latest runs of the apply and drift-check pipelines on the default branch, as a service hook would name them | 2026-10-30 | P2-15 (#114). Applies and drift checks finish without inbound access to Quai, at the next poll. A plan's details (resources, cost, policies) still need the `quai report` step to reach Quai |
| Which repository M1 is accepted on, while no pilot repository is available | **The stand-in `pilot-infra`** in the sandbox organization (synthetic VM files, Terraform stacks and pipelines, P2-13), until a real repository is available | 2026-10-30 | The stand-in and its pipelines and policies stay; a real repository is onboarded with the [same steps](../operations/deployment-and-operations.md#onboarding-an-azure-devops-repository), its type written from its own files and variables |
